## 1. SYNTHÈSE EXÉCUTIVE

**État général : 🔴**

Le projet présente une architecture backend solide (Onion Architecture) avec des algorithmes métier avancés (DBSCAN, bilans hydriques), mais souffre de **vulnérabilités de sécurité critiques** (secrets exposés, JWT hardcodé, privilège-escalation à l'inscription), d'une **couverture de tests quasi-nulle** (0 test sur ~60 modules de logique métier), et de **désynchronisations graves entre modèles ORM et logique domaine** (champs manquants, doublons de colonnes, relations absentes).

**Dette technique estimée : 25–35 jours/homme** pour atteindre un niveau production-ready.

**Recommandation majeure : Correctifs ciblés de sécurité immédiatement, puis refactor ciblé sur la couche modèles/domaine et mise en place de la suite de tests.**

## 4. POINTS "HUMAN REQUIRED"

> Ces points nécessitent une décision humaine — l'auditeur ne peut pas trancher seul.

### HR-1 — Règle métier implicite : valeurs des seuils hydriques
**Fichiers** : `domain/logic/stress_hydrique.py:32-38`, `domain/logic/sante.py:32-35`, `domain/logic/stress_sanitaire.py:60-92`  
Les seuils de stress (`0.3`, `0.6`, `15°C`, `24°C`, `0.5`, `2.0`) semblent issus d'une expertise agronome mais ne sont documentés nulle part. **Question** : ont-ils une base scientifique publiée ? Peuvent-ils varier selon le type de plante ou le biome ? → Nécessite validation par un expert domaine.

### HR-2 — Architecture : double source de vérité frontend/backend pour la météo
`front_end/src/services/weatherServices.js` appelle **directement** l'API OpenWeatherMap depuis le navigateur, contournant le backend. Le backend a aussi sa propre intégration météo (`infrastructure/services/meteo_open_meteo.py`). **Question** : est-ce intentionnel (réduction de latence) ou une duplication accidentelle ? → Décision d'architecture requise.

### HR-3 — Données de simulation vs données réelles
`infrastructure/services/capteur_hybrid_service.py` est un simulateur de capteurs IoT. Il n'est pas clair si c'est la seule source de données en production ou si une vraie intégration IoT est prévue. La présence du dataset `inaturalist/` (ML) suggère une roadmap ML. **Question** : quelle est la roadmap des capteurs réels ? → Impact majeur sur l'architecture.

### HR-4 — Choix base de données : SQLite en production ?
`infrastructure/database.py` utilise SQLite avec `check_same_thread=False`. Le `docker-compose.yml` racine ne monte pas de volume persistant pour la base. Le fichier `green_guard.db` est committé dans le dépôt git (modifié selon `git status`). **Question** : SQLite est-il accepté pour la production ou faut-il migrer vers PostgreSQL ? → Décision critique avant déploiement.

### HR-5 — Incohérence doc/code sur les use cases
`documentation/Documentation_Usecases.md` décrit deux use cases pour `generer_bilans_hydriques_journaliers`. Le code correspondant (`application/use_cases/generer_bilans_hydriques_journaliers.py`) existe, mais les étapes décrites dans la doc ne correspondent pas exactement à l'implémentation (champs différents, pas de gestion d'erreur documentée). **Question** : la doc est-elle la référence ou le code ? → Aligner ou décider lequel est la source de vérité.

### HR-6 — Rôle admin par défaut dans `create_user.py`
Le script `back_end/create_user.py` crée un compte `admin@demo.com` / `admin123`. **Question** : ce compte existe-t-il dans la base de données SQLite committée (`green_guard.db`) ? Si oui, c'est une backdoor active en production. → Vérifier et supprimer si présent.

### HR-7 — Dataset iNaturalist : usage prévu non documenté
Le dossier `inaturalist/` contient ~9 549 observations biologiques avec embeddings ResNet50. Aucun code ne l'utilise actuellement. **Question** : s'agit-il d'un futur module de classification de plantes ? Est-il dans le périmètre du projet actuel ? → Décision de roadmap.
